Привет! 
Отличный вопрос — ты столкнулся с классической особенностью работы межзонных политик (zone-based firewall) 
на маршрутизаторах Eltex (и многих других вендоров).

Давай разберем по полочкам, почему так происходит.

### Краткий ответ:

**Это не трюк Eltex, а ожидаемое поведение любого stateful межзонного фаервола.** 
Всё упирается в то, как политики безопасности (`security zone-pair`) обрабатывают трафик в зависимости от зоны, 
в которую помещен интерфейс (или туннель).

---

### Подробное объяснение:

#### 1. Ситуация: Туннели VTI в зоне `UNTRUST` (не работает)

*   **Логика обработки трафика:**
    1.  Пакет от `BR1` (172.16.1.10) к `BR2` (172.16.2.20) приходит на HUB через `vti5`.
    2.  Поскольку `vti5` находится в зоне `UNTRUST`, пакет считается пришедшим *ИЗ* зоны `UNTRUST`.
    3.  HUB смотрит таблицу маршрутизации и видит, что путь до сети `172.16.2.0/24` — через другой туннель, например, `vti6`,
	который тоже в зоне `UNTRUST`.
    4.  Чтобы отправить пакет обратно в ту же самую зону (`UNTRUST`), фаервол применяет политику **`zone-pair UNTRUST self`**.
    5.  Смотрим правила в `UNTRUST self`. Там есть разрешения для IKE, ESP, DNS, ICMP и т.д.,
	но **нет универсального разрешающего правила для всего TCP/UDP-трафика между туннельными интерфейсами**.
    6.  Пакет отбрасывается фаерволом на этапе межзонной политики. **Связности между BR1 и BR2 нет.**

*   **Суть проблемы:** Трафик между spoke-маршрутизаторами проходит через HUB "по горизонтали", 
внутри одной и той же зоны (`UNTRUST` -> `UNTRUST`).
 Для этого трафика должна существовать и быть разрешающей политика `self` для этой зоны.
 В вашей конфигурации такой политики нет.

#### 2. Ситуация: Туннели VTI в зоне `TRUST` (работает)

*   **Логика обработки трафика:**
    1.  Пакет от `BR1` приходит на HUB через `vti5`. Теперь `vti5` в зоне `TRUST`. Пакет считается пришедшим *ИЗ* зоны `TRUST`.
    2.  HUB маршрутизирует его на `vti6` (в `BR2`), который тоже в зоне `TRUST`.
    3.  Чтобы отправить пакет из зоны `TRUST` обратно в зону `TRUST`, фаервол применяет политику **`zone-pair TRUST self`**.
    4.  Смотрим правила в `TRUST self` (например, в конфиге `vesr124-1-2`):
        ```bash
        security zone-pair TRUST self
          rule 50
            action permit
            match protocol tcp # Разрешает весь TCP
            enable
          exit
        exit
        ```
        Там есть правило 50, которое **разрешает весь TCP-трафик**. 
		Аналогично, правило 20 в `TRUST UNTRUST` разрешает весь UDP. 
		Этого достаточно для прохождения практически любого пользовательского трафика.
    5.  Пакет успешно проходит. **Связность между BR1 и BR2 есть.**

*   **Суть решения:** Перенос туннелей в зону `TRUST` заставляет трафик между spoke'ами идти по пути `TRUST -> TRUST`.
 Для этой пары зон у вас случайно (или намеренно) настроена более разрешающая политика (`rule 50`),
 которая и позволяет трафику проходить.

---

### Что делать? (Варианты решения)

Вам не обязательно переносить туннели в `TRUST`. Есть более правильные и безопасные способы:

1.  **Правильный способ (рекомендуется):** Создать отдельную зону для туннелей, например, `VPN`.
    *   Поместить все VTI-интерфейсы в эту новую зону.
    *   Настроить строгую политику `VPN self`, разрешающую только тот трафик,
	который должен ходить между вашими филиалами (например, целиком или только определенные протоколы).
    *   Настроить политики `VPN to TRUST` и `TRUST to VPN` для доступа с LAN филиалов к ресурсам в центральном офисе (если это нужно).
    *   Это самый чистый и безопасный подход, он обеспечивает изоляцию и контроль.

2.  **Быстрый способ (но менее безопасный):** Добавить разрешающее правило в политику `UNTRUST self` на HUB-устройстве.
    *   В конфигурацию `security zone-pair UNTRUST self` нужно добавить правило, аналогичное правилу 50 в `TRUST self`:
        ```bash
        security zone-pair UNTRUST self
          rule 100
            action permit
            match protocol tcp
            enable
          exit
          rule 101
            action permit
            match protocol udp
            enable
          exit
        exit
        ```
    *   После этого трафик между туннелями в зоне `UNTRUST` будет разрешен.

Отличное уточнение! Вы абсолютно правы, и это очень важный момент. Давайте разберем цепочку обработки пакета на HUB-маршрутизаторе (vesr124-1-2) более детально.

Вы верно заметили, что процесс состоит из двух основных этапов: обработки внешнего IPsec-пакета и обработки внутреннего инкапсулированного пакета.

Детальная цепочка обработки пакета от BR1 к HUB
Предположим, на BR1 (vesr124-1-3) хост 172.16.2.10 хочет отправить пакет хосту 172.16.1.20 на BR2 (vesr124-1-2).

1. Этап: Доставка внешнего IPsec-пакета до HUB

Пакет с данными (src=172.16.2.10, dst=172.16.1.20) попадает в IPsec-туннель на BR1.

BR1 инкапсулирует его во внешний IPsec-пакет: src=10.10.20.2 (WAN-адрес BR1), dst=10.10.10.2 (WAN-адрес HUB).

Этот внешний пакет отправляется через физический интерфейс gi1/0/1 BR1 и приходит на физический интерфейс gi1/0/1 HUB.

Ключевой момент: Интерфейс gi1/0/1 HUB находится в зоне UNTRUST. Фаервол проверяет этот пакет по политике UNTRUST -> self, так как его назначение — сам маршрутизатор (на IP 10.10.10.2).

Политика UNTRUST self разрешает протоколы ESP (rule 40) и IKE (rule 35), поэтому пакет проходит и передается на обработку IPsec-стеку.

2. Этап: Обработка внутреннего пакета после расшифровки

IPsec-стек HUB принимает пакет, проверяет его аутентичность, расшифровывает и извлекает оригинальный внутренний пакет: src=172.16.2.10, dst=172.16.1.20.

Ключевой момент: Расшифрованный пакет "вводится" в операционную систему маршрутизатора через виртуальный интерфейс туннеля vti5.

Теперь именно это определяет зону! Так как пакет поступил на интерфейс vti5, а этот интерфейс находится в зоне TRUST, то пакет считается пришедшим ИЗ зоны TRUST.

Далее процесс идет, как я описывал ранее:

Маршрутизатор смотрит в таблицу маршрутизации для адреса 172.16.1.20.

Он находит маршрут ip route 172.16.1.0/24 tunnel vti 5 (в вашем конфиге) или, что более вероятно для трафика между филиалами, маршрут через другой туннель, например, ip route 172.16.2.0/24 tunnel vti 5 на BR2 и ip route 172.16.1.0/24 tunnel vti 6 на HUB.

HUB должен отправить этот пакет обратно в зону TRUST (через vti6), чтобы доставить его на BR2.

Для перехода TRUST -> TRUST применяется политика zone-pair TRUST self, которая его пропускает (благодаря rule 50).

Пакет снова инкапсулируется в IPsec и отправляется на WAN-адрес BR2.

Итог и ответ на ваш вопрос
Вы совершенно правы. Ваше замечание более точно.

"Пакет от BR1 приходит на HUB через gi1/0/1 (в зоне UNTRUST) в виде зашифрованного ESP-пакета.
 После успешной расшифровки оригинальный пакет поступает на обработку фаерволу через интерфейс vti5,
 который находится в зоне TRUST. Поэтому фаервол считает, что пакет пришел ИЗ зоны TRUST."

Таким образом, зона для оригинального (внутреннего) трафика определяется не исходным WAN-IP,
а тем виртуальным интерфейсом (VTI), на который этот трафик поступил после расшифровки. 
Это и есть причина того, почему перенос VTI-интерфейсов между зонами так кардинально меняет поведение фаервола.
